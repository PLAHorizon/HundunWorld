### 1) XA4301 × 16 —— Horizon.Game.GengDi (net10.0-android)

**根因（非猜测，已读 SDK 源码确认）**：
`C:\Program Files\dotnet\packs\Microsoft.Android.Sdk.Windows\36.1.43\Sdk\AutoImport.props:57`

```xml
<AndroidNativeLibrary Include="**\*.so" Exclude="$(DefaultItemExcludes);$(DefaultExcludesInProjectFolder)" />
```

Android SDK 对**项目目录**做 `**\*.so` 全局通配，只排除 bin/obj 等默认输出目录。
`Horizon.Game.GengDi\publish\` 与 `\output\`（各 26MB，桌面端 `dotnet publish` 残留、
已被 .gitignore 忽略、无任何脚本引用）内含
`runtimes/<rid>/native/libe_sqlite3.so`（来自 LiteDB→SQLitePCLRaw 传递依赖）。
这些 .so 被当成 Android 原生库，而 `runtimes/linux-x64/native` 不是合法 ABI 目录名
→ 报 "无法确定本机库的 ABI"。每个目录 8 个 RID × 2 目录 = 16 条错误。

**修复**：`Horizon.Game.GengDi/Horizon.Game.GengDi.csproj` 在项目体（即 AutoImport.props
导入之后）显式剔除：

```xml
<ItemGroup>
  <AndroidNativeLibrary Remove="publish\**" />
  <AndroidNativeLibrary Remove="output\**" />
</ItemGroup>
```

**验证方法（重要，比全量构建快得多）**：
`dotnet build Horizon.Game.GengDi/Horizon.Game.GengDi.csproj "-getItem:AndroidNativeLibrary" "-p:TargetFramework=net10.0-android"`
→ 修复后返回 `{"Items":{"AndroidNativeLibrary":[]}}`。

**遗留建议**：`publish/`、`output/` 属孤儿产物，建议直接删除（52MB）；已在回复中提示，
未代为删除（破坏性操作需用户确认）。根目录 `publish\GengDi` 才是 build-installer*.ps1 的产物目录。

## 追加：排查网关 checksum mismatch（2026-09-20 12:32:55 三条）

**现象**：`Horizon.Game.Gateway` 日志
`HorizonMessageInfo.OnParsingBody: checksum mismatch, expected=28336, actual=28945/28949/28956`
同 1 毫秒内 3 条 → 同一批到达/同一段 TCP 数据。

### 协议事实（本次核清，作为后续排查基线）

- 线路帧固定 **8 字节头**：`[0-3] 载荷长度 LE` + `[4] 消息类型(>255 按低位截断)` + `[5] 压缩标志` + `[6-7] 校验和 LE`。
- 校验和算法**唯一实现**：`HorizonProtocol.CalculateChecksum` = 载荷各字节累加后 `& 0xFFFF`
  （`Horizon.Game.Message/Network/HorizonMessagePacket.cs:275`）。
- `HorizonMessageInfo` 的 `_expectedChecksum` 只来自头 [6-7]；`actual` 由收到的载荷现算。

### 全仓帧写入/读取点审计结论：**源码层自洽**

枚举了全部 5 个写入方与全部读取方，**都按同一 8 字节偏移写载荷、都对 wire 载荷算校验和**：
- `Horizon.Game.Core/Adapters/HorizonMessageAdapter.cs`（服务端，`WrapPacket`）
- `HundunWorld/Source/Game/Network/Adapters/HorizonMessageAdapter.cs`（Flax 客户端）
- `Horizon.Game.Message/Network/SyncHandshakeWire.cs`（共享，GengDi 客户端用）
- `Horizon.Game.GengDi/Core/Services/ImGatewayContactClient.cs`、`Horizon.IM.Core/Adapters/IMMessageAdapter.cs`（IM 侧）
- DS 上行（`DsUplinkServer`）用的是自有 `DsFrameReader` 长度前缀，**不经过** `HorizonMessageInfo`，可排除。

⇒ 校验和不匹配只可能来自：(a) 发送方按**非 8 字节头**成帧；(b) 接收方切片错位；
(c) 发送/接收方**二进制与源码不一致**。TCP 字节不会自己变。

### 本次修掉的一个真地雷（会产生与现象完全一致的日志）

`HorizonMessageInfo.Build<TByteBlock>` 写的是**旧线格式**「4 字节长度前缀 + MemoryPack 体」
（无类型/压缩标志/校验和），而该类通过 `CustomFixedHeaderDataHandlingAdapter` 注册为**可发送**
请求信息（Flax 客户端适配器 `CanSendRequestInfo = true`）。一旦走 TouchSocket 强类型发送：
对端按 8 字节头解析 → 头 [6-7] 取到的是**载荷第 2-3 字节**（同类型消息恒定！）
→ 出现"expected 恒定、actual 随载荷微变"。**已改为与各写入方逐字节同构的 8 字节头**
（`span[4]` 类型截断、`span[5]=0` 不压缩、`CalculateChecksum`）。当前无调用方，改动零风险。

### 新增诊断（下次复现即可定位）

1. `HorizonMessageInfo.OnParsingBody` 校验和不匹配时追加：
   `bodyLength`、`compressed`、`header=[8 字节十六进制]`、`bodyHead=[载荷前 32 字节十六进制]`。
   存原始头用 `ulong _rawHeader`（值类型），**热路径零分配**，仅错误路径格式化。
2. `ClientPacketPipeline` 的"收到无法解析的消息帧"告警补上 `Remote={RemoteAddress}`，
   可直接看出是**哪个客户端**发的。

### 部署拓扑坑（重要，会导致"客户端/编辑器跑旧二进制"）

- Flax 编辑器运行时从 **`C:\Program Files (x86)\Flax\Flax_1.12\Binaries\Tools\`** 加载
  `Horizon.*.dll`；`Horizon.Game.ECS` / `Horizon.Game.ECS.Arch` 有 `[CopyToFlax]` 目标自动同步，
  但**因 Program Files 权限一直被拒绝**（`MSB3021: Access to the path ... is denied`），
  这两个 DLL 长期是旧的运行时副本。
- `HundunWorld/Source/Game.csproj` 以 `HintPath` 引用 `HundunWorld\Output\Windows\Horizon.Game.Message.dll`
  （非 ProjectReference）：改共享工程公共 API 后必须手工同步该目录。
- 网关改完只需重新构建/重启网关本身（读自己的 `bin`），不需要动 Flax。

## ★ 终局根因：LZ4Pickler 符号绑定错位（承接上节 checksum mismatch，2026-09-20）

上一节审计了帧格式、`CalculateChecksum`、5 个读写点，结论「源码层自洽」，推测落入
「(c) 发送/接收方二进制与源码不一致」。**本次把 (c) 具体化了，且证据是逐字节级的。**

### 现象与判据

用户报「登录成功但角色列表恒为空，有实际角色」。实测链路：

| 侧 | 日志 | 含义 |
|---|---|---|
| 客户端 | `[SendMessageAsync] 消息包发送成功: CharacterList` | 自认为发出去了 |
| 客户端 | `[CharacterManager] 开始加载角色列表` → `角色列表为空` | 从未收到响应 |
| 网关 | `OnParsingBody: decompression failed (malformed or exceeds 8388608 bytes), compressed=True, wireSize=371` | **包被拒** |
| 网关 | `ConnectionLifecycleManager 连接 NN-00-00-00 首包超时` → 断开 | 首包从未成功解析 |
| 客户端 | `[Network]: 创建角色请求失败` | 连创建角色也失败（全局性，非单接口） |

**关键判据（解析顺序）**：`OnParsingBody` 是 **先校验和（L191）→ 后解压（L199）**。
能走到 "decompression failed" 分支，说明该包**校验和是通过的**、长度也匹配
⇒ 字节没被改写，**只是「标记 compressed=1 的内容不是接收方认得的 LZ4」**。
这一条直接排除了「传输损坏 / 切片错位」，把矛头指向 **压缩实现不一致**。

同理，那 1524 条 `checksum mismatch` 是**首包解析失败后的缓冲重扫**产物
（同一时刻、expected 恒定、actual 随偏移漂移），**不是**独立根因。

### 根因：仓内 4 份 LZ4Pickler，客户端静默绑到了 K4os 版

仓库里有**四份**同名 `LZ4Pickler`：

| 实现 | 线格式 |
|---|---|
| `Horizon.Game.Message.Utilities.LZ4Pickler`（协议权威，网关**解析**用） | `[4B int32 原长][LZ4块 或 原文]` |
| `Horizon.Game.Core.Utilities.LZ4Pickler`（网关**发送**用，显式别名） | 同上 |
| `Horizon.IM.Core.Utilities.LZ4Pickler` | 同上 |
| **`K4os.Compression.LZ4.LZ4Pickler`**（K4os 包自带！） | `[1B seed][7bit 变长原长][LZ4块]` |

客户端 `HundunWorld/Source/Game/Network/Adapters/HorizonMessageAdapter.cs` 原本写的是
`using K4os.Compression.LZ4;` 且**未起别名** → C# 名字解析把 `LZ4Pickler` 静默绑到
**K4os 版**。于是客户端按 K4os 格式压缩，网关按 Horizon 格式解压 → 必败。

**为什么极难发现**：
1. K4os 版 `Pickle(byte[])` / `Unpickle(byte[])` 与协议版**签名一致** ⇒ **编译零警告**；
2. body ≤ 256 字节的包不压缩（登录/握手）⇒ 登录正常，只有业务包挂掉，
   现象伪装成「业务接口问题」而非「协议问题」；
3. 源码里字面上写的都是 `LZ4Pickler.Pickle(...)`，**肉眼看两遍也看不出差别**。

## 修复 IM 网关并发集合损坏（IMGatewayPushService）

**报错**（用户贴栈）：
```
System.InvalidOperationException: Operations that change non-concurrent collections must have
exclusive access. A concurrent update was performed on this collection and corrupted its state.
  在 System.Collections.Generic.HashSet`1.Add(T item)
  在 Horizon.IM.Gateway.Services.IMGatewayPushService.EnsureUserSessionAsync() 第 113 行
  在 Horizon.IM.Gateway.Network.IMNetworkServer.OnDataReceived() 第 290 行
  ← TouchSocket TcpService/TcpSessionClient 接收回调链
```

### 根因：共享可变状态暴露在并发入口上

`IMGatewayPushService` 是**单例服务**，而它的方法是**直接从 TouchSocket 接收回调调用**的
（`IMNetworkServer.OnDataReceived` → `EnsureUserSessionAsync`）。接收回调跑在**线程池**上，
可被**多连接 / 多消息同时进入**。而订阅表原本是普通集合：

```csharp
private readonly HashSet<ulong> _subscribedUsers = new();   // ❌
```

并发 `Add`（订阅）/ `Remove`（断开）会损坏内部桶结构。注意它**不一定每次都抛**——
也可能静默丢条目或遍历死循环，所以"偶发"是这类缺陷的典型特征。

### 修复（`Horizon.IM.Gateway/Services/IMGatewayPushService.cs`）

1. `HashSet<ulong>` → **`ConcurrentDictionary<ulong, byte>`**（用"键即成员"表达集合），
   语义对齐：`Add→TryAdd`、`Remove→TryRemove(out _)`、`ToList→Keys.ToArray()`、`Clear` 不变。
2. `StopAsync` 的遍历改为**先取快照**（`Keys.ToArray()`）：关闭期间仍可能有在途回调并发改动。
3. **顺带修掉同一路径上的第二个竞态**：`StartAsync` 的
   「检查 `_observerReference == null` → 创建并赋值」**非原子**。两个线程同时通过检查会各自
   建一个 Observer，其中一个引用被覆盖后无人引用，而 grain 可能恰好订阅到被丢弃的那个
   → **该用户主动推送永久失效且无任何异常**。已用 `lock (_observerLock)` 包裹（锁内无 await），
   并把 `_observerReference` 标为 `volatile`（跨线程读写需可见性，否则工作线程可能长期读到缓存的 null）。

### 同类缺陷审计（结果：这是唯一一处）

并发源 = TouchSocket 接收回调 + Orleans Observer 回调。扫描命令：

```bash

  Horizon.IM.Gateway/ Horizon.IM.Core/ Horizon.Game.Gateway/ --include=*.cs \
  | grep -v "/obj/" | grep -vE "Concurrent|Immutable|IReadOnly"
```

| 嫌疑点 | 结论 |
|---|---|
| `IMGatewayPushService._subscribedUsers` | ❌ **本次根因，已修** |
| `Game.Gateway/Services/SimpleServiceImplementations.cs` `SessionManager` | ✅ 已有 `_lock` 且全程加锁 |
| `Game.Gateway/Services/DSRegistry.cs` `_entries` | ✅ 8 处 `lock (_lock)` |
| `Game.Gateway/Services/GrayComparisonHostedService.cs` 统计字典 | ✅ 4 处 `lock (_lock)` |
| `Game.Gateway/Network/GameConnection.cs` `_properties` | 每连接私有，无跨线程共享 |

### 新增回归测试的设计取舍

`Horizon.IM.Gateway.Tests/IMGatewayPushServiceTests.cs` 新增用例：64 个用户 × 3 次并发调用，
断言不抛异常，之后再做一次 `订阅 → 断开` 往返（覆盖 `TryRemove` 与快照遍历路径）。

- **不用 `Task.Run` + `Barrier` 对齐**：`Barrier.SignalAndWait` 会**阻塞线程池线程**，
  192 个阻塞任务可能触发线程饥饿甚至卡到超时。改为直接并发发起（不套 `Task.Run`）——
  每个调用同步跑到第一个 await（grain 调用）再让出，192 个调用几乎同时进入方法体，
  并在两次 grain 往返后自然交错到临界区。既贴近 TouchSocket 回调的真实形态，又不额外占线程。
- **不追求"必然复现"**：并发缺陷本质概率性。该用例定位是**回归护栏**——
  修复后恒绿；若有人把并发集合改回普通集合，风暴下极易由红。

## 修复「登录后角色列表恒为空」— 客户端连接建立层（跨层排查）

接在 LZ4Pickler 修复之后。用户报「无法正常登录」。**这次卡在连接建立层，与编解码无关。**

### 先排除的两个误判（记录为经验）

1. **网关 `[NetDiag] 数据接收` 日志被限流为 10 秒一次**
   （`ClientPacketPipeline.cs:124` 的 `_lastReceiveDiagTicks` + `ReceiveDiagInterval`）。
   ⇒ **"日志里没有某类型的收包记录"不等于"服务端没收到"**。我一度据此误判
   "CharacterList 从未到达网关"，实为限流吞掉了日志。查收包必须先看限流注释。
2. **网关 `ClosedEvent` 日志可能被懒初始化阻塞而严重滞后**：本次
   `CharacterFingerprintService Redis 延迟初始化成功`(13:15:13.833) 与
   `客户端断开`(13:15:13.839) 相差 5ms，而客户端侧早在 13:14:53.723 就断了
   ⇒ 20 秒差是**清理路径被 Redis 首次初始化阻塞**，不是真实的断开时刻。
   ⇒ **比对两侧时间戳时，别把网关侧的清理日志时间当作断开时刻。**

### 根因链（两处可证缺陷）

**缺陷 1：`ReconnectionManager.MarkConnected()` 不重置心跳失败计数**

`_consecutiveHeartbeatFailures` 原本**只在 `UpdateHeartbeat()`（收到服务端应用层数据）时**归零。
而玩家未进游戏时服务端**不主动下发任何数据**（无角色、无快照）⇒ 计数只增不减。
客户端日志铁证：`心跳超时: 30989ms，连续失败 24/5` → `25/5` → … → `31/5`
（阈值仅 5，却持续增长，说明跨多次重连从未归零）。

后果：`CheckHeartbeat`（周期 3s）在 `CurrentState==Connected` 且计数已超阈值时，
会调用 `_disconnectFunction()` **主动关闭连接**并 `HandleDisconnect()`。
⇒ 新建立的连接继承上一条连接的"欠账"，随时被判定断线。

**缺陷 2：`ConnectOnDemandAsync` 是死代码，登录路径只"等"不"连"**

- `NetworkManager` 构造时把重连的 `connectFunction` 定义为**仅做可达性探查、不建持久连接**
  （注释明说：为避免玩家未进游戏→服务端首包超时关连接→无限重连循环）。
- 设计上"真正的持久连接"应由 `ConnectOnDemandAsync` 在用户主动进游戏时建立，
  **但全仓无任何调用点**（所有引用都是注释）。
- `AuthenticationManager.FinalizeLoginAsync` 的角色列表重试循环**只 `WaitForConnectionAsync`**，
  于是永远等不到：状态机会报 Connected、甚至打印"重连成功"，
  而客户端日志同时打 `[RaiseReconnectionSucceededSafely] _client 为空，跳过重连成功处理`
  —— **状态与真实连接背离**，这就是"列表恒为空"的直接原因。

### 修复

| 文件 | 改动 |
|---|---|
| `HundunWorld/Source/Game/Network/ReconnectionManager.cs` | `MarkConnected()` 增加 `_consecutiveHeartbeatFailures = 0;`——**新连接不继承旧连接的心跳欠账**。语义上该计数是"当前这条连接连续超时次数"，换连接必须从零计 |
| `HundunWorld/Source/Game/UI/Authentication/AuthenticationManager.cs` | `FinalizeLoginAsync` 重试循环：连接未就绪时由「只等待」改为**主动 `ConnectOnDemandAsync()`**（探查→真正 ConnectAsync→MarkConnected），失败再短等待+退避重试 |

> 关于「不取消断线超时计时器」的既有取舍：那条规则针对的是 **`_disconnectTimeoutCts`**，
> 防止"TCP 连上但无数据→服务端关闭→无限重连"；本次重置的是**超时判定的前置门限**，
> 不取消计时器，因此不会让上述循环复活。

### 复用工具（本轮新增）

`.dbg/dec.py`：还原 Flax 客户端日志的**混合编码**。
该日志多数行是 UTF-16LE，但部分行由"增强日志桥"以 **UTF-8 字节**写进 UTF-16 流，
按 UTF-16LE 读出即为乱码（中文呈现为"UTF-8 被当 GBK"的样子）。
还原法：`line.encode('utf-16-le').decode('utf-8')`。
用法：`python .dbg/dec.py <Log_*.txt>`。
**注意**：`iconv` 会在遇到坏序列时提前中断，只输出前几百行，极易误判为"日志里没有该记录"。
