### 根因链（三段，均有日志佐证）

1. `AuthenticationManager.FinalizeLoginAsync` 中，`await ConnectOnDemandAsync()/SendMessageAsync()`
   的续体回到**线程池线程**，随后直接调用 `GameSceneManager.GetOrCreate()`。
2. 实例若在此处首次创建 → 非主线程 `new EmptyActor + Level.SpawnActor` 被 Flax 拒绝
   → `OnAwake`/`FindRootScene` 未执行 → `_rootScene` 恒为 `null`。
3. `_rootScene == null` 使所有 `scene != _rootScene` 判断失效：
   - `TransitionTo` 的「追踪当前子场景」把 RootScene 当子场景；
   - `DirectLoadTargetScene → SafeUnloadScene` 的 `if (scene == _rootScene)` 保护因 null 失效
     → **真的卸载 RootScene**；
   - 切换完成事件随场景消失 → `_isTransitioning` 永远为 `true` → 之后所有 `TransitionTo`
     都被「场景正在切换中」拒绝。
   ⇒ 角色选择场景永远加载不出来，所以「角色列表拿到了也不显示」。

### 修复

| 文件 | 改动 |
|---|---|
| `Source/Game/UI/GameSceneManager.cs` | 新增 `EnsureRootSceneResolved()`（惰性解析，`TransitionTo`/`SafeUnloadScene`/`Reset` 前调用）；新增 `IsUnloadableSubScene()` 统一排除 RootScene／承载本脚本的场景／过渡场景，替换 5 处 `scene != _rootScene && !IsTransitionScene(scene)`；`SafeUnloadScene` 加三重保护（含「`_rootScene` 未解析时保守拒绝卸载」）；`TransitionTo` 加**切换卡死看门狗**（`_transitionStartTime` + 8s 阈值，超时强制复位而非拒绝请求）；新增公共 `ForceResetTransition(reason)`；`DirectLoadTargetScene` 的 `Level.LoadSceneAsync` 由 `Task.Factory.StartNew`（线程池）改回**主线程直接调用** |

## ★ 终局根因（19:26 复现确认）：脚本输出目录缺少 Microsoft.Extensions.Logging.Abstractions.dll

### 证据：上一轮加的诊断日志一次命中

```
[OnClientDisconnected] 断开诊断: CloseMessage=Could not load file or assembly
'Microsoft.Extensions.Logging.Abstractions, Version=10.0.0.0, Culture=neutral,
PublicKeyToken=adb9793829ddae60'. 系统找不到指定的文件。,
_isDisposing=False, ctsCancelled=False, clientOnline=False, 调用栈:
   at HundunWorld.Game.Network.NetworkManager.OnClientDisconnected(...)
   at TouchSocket.Sockets.TcpClientBase.ReceiveLoopAsync(...)
```

**断开发生在 TouchSocket 的接收循环里** ⇒ 响应**已经到达**客户端，客户端在解析消息时抛
`FileNotFoundException`，接收循环终止 → 连接关闭。
所以「发完请求 ~30ms 就断」的真实含义是**「响应到达后立刻崩溃」**，
这也解释了为什么客户端永远没有「收到角色列表响应」的日志。

### 为什么缺

- 依赖扫描（用 `System.Reflection.Metadata` 读 AssemblyRef，脚本见下方「复用工具」）显示：
  `Microsoft.Extensions.Logging.Abstractions` 被 `Horizon.Game.Message.dll`、
  `Horizon.Game.Core.dll`、`Horizon.Game.ECS.Arch.dll` 引用，
  而 **`Horizon.Game.Message` 是客户端必然加载的消息类型程序集**。
- 四个目录都**有**这个 DLL（Flax Tools / Output/Windows / 各服务端 bin），版本均为 10.0.0.0，
  **唯独脚本输出目录 `Binaries/GameEditorTarget/Windows/x64/<Config>/` 没有**。
- **根因**：`Cache/Projects/Flax.Build.CSharp.targets` **把 `Build` 目标整个覆盖为
  `Exec Flax.Build CLI`**，于是 `Microsoft.NET.Sdk` 标准的
  「解析引用 → 拷贝 CopyLocal 依赖到输出目录」流程**根本不执行**。
  输出目录里的依赖 DLL 只是历史快照（实测时间戳：ObjectPool 2025-10-24、
  Options/Primitives 2025-12-13、TouchSocket 2026-02-01），**新增依赖不会被同步**。
- `Game.csproj` 里其实有 `Microsoft.Extensions.Logging.Abstractions` 的 `<Reference>`，
  但**只在 `Game.Windows.*` 打包配置中声明**，编辑器配置（无 Condition 那组）漏了。

### 修复

| 位置 | 改动 |
|---|---|
| `HundunWorld/Source/Game.csproj` | ① 在编辑器配置用的无 Condition ItemGroup 中补 `<Reference Include="Microsoft.Extensions.Logging.Abstractions">`（HintPath 指向 Flax Tools）；② 新增 `SyncFlaxScriptDependencies` Target（`AfterTargets="Build"`），Flax 构建后把该 DLL 拷进 `$(OutputPath)` |
| 输出目录 | 手动补齐 `Binaries/GameEditorTarget/Windows/x64/{Debug,Development}/` —— 依赖 DLL 是运行时加载，**无需重新编译脚本，重启 PIE 即生效** |

### 验证

| 项 | 结果 |
|---|---|
| `Editor.Windows.Debug` 编译 | **0 错误 / 0 警告**，`AfterTargets` 生效（DLL 自动出现在输出目录） |
| 两个配置输出目录 | 均含 `Microsoft.Extensions.Logging.Abstractions.dll`（共 27 个 DLL） |

### 排查心得（本轮最值钱的三条）

1. **「数据没到」和「数据到了但处理时崩了」在业务日志上长得一模一样**（都没有任何响应日志）。
   区分办法：看断开是否发生在 **TouchSocket 的 `ReceiveLoopAsync` 调用栈**里 —— 是则说明数据已到达。
2. `ClosedEventArgs.Message` 会把 `FileNotFoundException` 的完整信息带出来，**这是本次破案的唯一关键**。
   给 `OnClientDisconnected` 打印 `e.Message` + 调用栈，收益极高，值得常驻。
3. **Flax C# 脚本项目的依赖不会由 MSBuild 自动同步**，必须在 `AfterTargets="Build"` 里自己拷；
   排查「运行时 FileNotFound」时，先对比脚本输出目录与 `Output/Windows` 的 DLL 差异。

### 复用工具（本轮新增）

`.workbuddy` 外的临时脚本，可复用于「输出目录缺哪些依赖」：
用 `System.Reflection.Metadata` + `PEReader` 读输出目录所有 DLL 的 AssemblyRef，
与目录内实际存在的程序集做差集（过滤 `System.*` / `netstandard` 等框架程序集）。

## ★ 重要纠正（20:13）：`Could not find an implementation` 在启动 ~60 秒内是**正常现象**

### 我之前误判了

上一轮把「自检 20 秒失败」当成「Client 解析表缺失」的证据 —— **这是误报**。

**证据来自项目自身的代码**（`Horizon.Game.Gateway/Services/`）：

```csharp
// KifaMarketDataFetcher.cs:45 / FlowerWeatherFetcher.cs:43 / DounanMarketDataFetcher.cs:126
// 等待 Orleans Silo 就绪：客户端 GetGrain<T>() 需要从 Silo 获取 grain 类型映射，
```

且网关日志里明确出现过 `Orleans Silo 已就绪（等待 32 次后成功）`。

⇒ **Client 的「接口 → Grain 类」映射由 Silo 通过 ClusterManifest 异步下发，
启动后数十秒（实测约 60s）内 `GetGrain` 报 `Could not find an implementation` 属正常。**
项目里那些 Fetcher 都为此写了重试等待。

**我的自检固定 20 秒就下结论 → 必然误报。**

### 所以真正的故障仍然是 60 秒后的 `TypeLoadException`

即：`GetGrain` 等到 Silo 就绪后能通过，但**调用时反序列化响应失败** ——
这才是需要 `AddAssembly` 修的那个问题（上一轮的改动方向是对的）。

### 本轮改动（`Horizon.Game.Gateway/Program.cs`）

把自检从「固定 20 秒探测一次」改为**轮询探测直到成功或 150 秒超时**：

```csharp
var deadline = DateTime.UtcNow.AddSeconds(150);
while (DateTime.UtcNow < deadline) { attempt++; try { GetGrain<...>(0); ✅ 通过; break; } catch { await Task.Delay(5000); } }
// 超时才输出失败 + ClusterManifest 诊断
```

失败分支再用**反射按类型名**查 `Orleans.Runtime.IClusterManifestProvider`，
打印 `IsAvailable` / `Current` / 各集合条目数，用于区分「manifest 没到位」与「manifest 里没有该 Grain」。

**踩坑（第二次踩同一类）**：`IClusterManifestProvider` 的命名空间是 **`Orleans.Runtime`**，
不是 `Orleans`。在 `Horizon.*` 项目里写 `Orleans.Xxx` 还可能被解析成 `Horizon.Orleans.*`，
**最稳的做法是用 `AppDomain.CurrentDomain.GetAssemblies()` + `GetType("全名", false)` 反射查找**，
既不依赖编译期命名空间，也不受 Orleans 版本差异影响。

编译：**0 错误 / 178 警告**，`Horizon.Game.Gateway.dll` mtime 20:13:47。

重启网关后**等约 2 分钟**，再看：
- `[自检] ✅ Grain 解析通过（第 N 次探测）` ⇒ 解析表正常；
- 若 2 分钟后仍 `❌` ⇒ 才是真问题，此时会附 ClusterManifest 诊断；

## ★ 追加（20:20）：发现并修复 `ShardFanoutSubscriber` 的重试窗口缺陷

### 观察

20:15:19 重启的网关，日志到 20:16:16 为止（之后网关停掉，**恰好差 3 秒没跨过 60 秒节点**，
所以 `[自检]` 与 Fetcher 的日志都没来得及产出，本轮无法验证 `AddAssembly` 效果）。

但这轮日志暴露了一个**确定的时序缺陷**：

```
ShardFanoutSubscriber：向 ZoneShard 0 订阅 fanout 失败（尝试 1/10）…（尝试 10/10）
ShardFanoutSubscriber：已达最大重试次数（10），进入循环但可能收不到该 shard 的推送
```

`ShardFanoutSubscriber.SubscribeAllAsync` 的退避是 `RetryBaseDelayMs(1000ms) × attempt`，
`MaxRetries = 10` ⇒ 总窗口 = 1+2+…+9 = **45 秒**。

而 Client 拿到 Grain 类型映射需要 **~60 秒**（见上文）。

⇒ **窗口天生不够，fanout 订阅在每次启动时必然失败**；
而 `IZoneShardGrain` 一直报同一个错，与 9-06 起的长期现象一致。
更严重的是：订阅失败意味着**游戏同步推送（ZoneShard fanout）一直没接上**。

### 修复（`Horizon.Game.Gateway/Services/ShardFanoutSubscriber.cs`）

新增对「启动期映射未就绪」的识别与长窗口：

```csharp
public const int StartupResolutionRetries = 40;      // 40 × 3s ≈ 120s
public const int StartupResolutionDelayMs = 3000;

private static bool IsGrainResolutionPending(Exception ex)
{
    for (var e = ex; e != null; e = e.InnerException)
    {
        if (e is ArgumentException && e.Message.Contains("Could not find an implementation", StringComparison.Ordinal))
            return true;
        if (e is TypeLoadException && e.Message.Contains("Unable to parse or load type", StringComparison.Ordinal))
            return true;
    }
    return false;
}
```

`SubscribeAllAsync` 内 `maxAttempts` 由 `const` 改为可变：
首次识别到该异常时放宽到 `StartupResolutionRetries`，并改用固定 3 秒间隔
（普通错误仍走原来的递增退避，不影响快速失败语义）。

编译：**0 错误 / 178 警告**，`Horizon.Game.Gateway.dll` mtime 20:20:04。

### 经验

**凡是在网关启动路径上调用 Grain 的地方，都必须考虑「启动后 ~60 秒内 Grain 映射不可用」，
重试总窗口应 ≥ 120 秒**。项目里 `FlowerWeatherFetcher / DounanMarketDataFetcher / KifaMarketDataFetcher`
已用「等待 Silo 就绪」循环处理，但 `ShardFanoutSubscriber` 漏了 —— 这类"部分组件记得、部分忘记"
的时序假设，最好收敛成一个公共等待助手，避免以后再漏。
