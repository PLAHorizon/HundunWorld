# 移动模拟的垂直单位口径：现状取证、修法与决策清单（2026-10-25）

> 关联：#101「跳跃高度仅 1.5cm：模拟层米/厘米口径不一致」。本文件只做取证、方案与回退设计，
> **不改代码**——按用户既有口径（大功能先方案文档 + 决策清单，确认后再写码）。

## 1. 现象与判据

- 实测：一次普通跳的顶点只有 **1.54 个世界单位**（约 1.5 cm），落地动画几乎看不出起跳。
- 这个数字可以从常量直接算出来：`h = v² / (2g) = 5.5² / (2×9.81) = 1.542`。

## 2. 单位证据（同一份代码里两套单位）

| 位置 | 数值 | 隐含单位 | 出处 |
|---|---|---|---|
| 角色 Prefab 的 `PlayerController.MoveSpeed` | **500** | cm/s | `Content/Prefabs/Character/CharacterRoot*.prefab` |
| 引擎默认重力 | **-981** | cm/s² | `FlaxEngine/Source/Engine/Physics/PhysicsSettings.h:65` |
| 世界几何/相机 | 角色身高约 175、相机 6253 | cm | 场景与 `3d-2` 取景记录 |
| `MovementFormula.Gravity` | **9.81** | m/s² | `Horizon.Game.Sim.Contracts/MovementFormula.cs:33` |
| `SimulationOptions.DefaultJumpImpulses` | **5.5 / 4.5 / 3.5** | m/s | 同上 `SimulationOptions.cs:19` |
| `MovementFormula.TerminalVelocity` | **50** | m/s | 同上 |
| `SimulationDefaults.HardSpeedCap` | **200** | m/s | 与客户端上报的 500 **直接冲突**（>200 即判 SpeedHack） |

结论：公式层按"米"写常量，位置空间与世界渲染按"厘米"用。于是：

1. 跳跃冲量 5.5 被当成 5.5 cm/s，跳跃顶点只有 1.54 cm；
2. 重力 9.81 被当成 9.81 cm/s²，下落也慢了 100 倍（这也是空中共时过长的原因之一）；
3. `HardSpeedCap = 200` 小于客户端正常上报的 `MaxSpeed = 500`，反作弊每帧都可能判超速
   （是否真的触发取决于 `MovementValidator` 是否被调用；`Horizon.Game.Sim` 内判定逻辑本身是 `>` 比较）。

## 3. 三种修法

### 方案 A（推荐）：公式与反作弊阈值统一改成厘米
- `Gravity: 9.81 → 981`；`TerminalVelocity: 50 → 5000`；`DefaultMaxSpeed: 6 → 500`
- `DefaultJumpImpulses: {5.5, 4.5, 3.5} → {550, 450, 350}`
- `SimulationDefaults`: `PositionEpsilon 0.5 → 50`、`HardSpeedCap 200 → 20000`、
  `MaxDynamicEpsilon 12 → 1200`、`TeleportDistanceThreshold 100 → 10000`
- `FormulaVersion: 3 → 4`（协议语义变了，握手必须拒旧客户端）
- 重新生成两条金轨迹 + 同步两处指纹常量（生成器在测试工程里：
  `DeterministicTraceGen.BuildFileContent(BuildTrace())` / `MultiEntityTraceGen.BuildFileContent(BuildTrace())`；
  `.freebuff/Verify` 已不在盘上，需要用测试工程内的生成器补一个一次性 runner）
- 预期：跳跃顶点 **1.54 → 154 单位（1.54 m）**；空中时间约 1.1 s；水平 500 cm/s 不再触发上限。

**代价 / 风险**
- 服务端（Silo 内的 `ZoneShardGrain`）与客户端必须**同批**升级；`FormulaVersion=4` 会拒掉旧客户端。
- 金轨迹与 3 处指纹要一起更新；`DeterministicReplayParityTests` / `DeterministicMultiEntityParityTests`
  的检查点数值会整体变化。
- 需要重启本地 Silo 并重建 Game/Editor 装配；在 UI 像素通路可用前，只能做**实测位置采样**验证
  （`actor_get` 逐帧读 Y），不能靠肉眼。

### 方案 B：ECS 保持米、渲染边界 ×100
- 只改 `LocalPlayerActorSyncSystem` / `RemotePlayerActor` / 地面采样器 / 点击寻路的坐标换算。
- 优点：不动共享公式与握手，服务端无需重启。
- 缺点：所有 ECS↔世界 的边界都要一次改全（远端、技能、AOI 分块、相机），漏一处就是半米/50 米级的错位；
  比方案 A 的爆炸半径更大，且会把"两套单位"永久留在架构里。**不推荐**。

### 方案 C：暂不修
- 保持现状并在文档里登记；但跳跃/下落时长与反作弊阈值都是错的，属于"玩法肉眼可见不对"，
  不宜长期保留。

## 4. 验收清单（选 A 时）
1. 单测：`StepVertical(0,0,550,1/60)` 的解析顶点 ≈ 154（容差 2），空中时间 ≈ 1.12 s。
2. 金轨迹：两条轨迹头部 `# FormulaVersion = 4`，再生成逐字节一致；两处指纹更新。
3. 握手：旧版本(3)被拒、4 通过（`HandshakeFormulaVersionTests` 新增一档）。
4. 反作弊：`MaxSpeed=500` 不触发 `HardSpeedCap`（单测）。
5. 实机：PIE 内 F9 起跳，`actor_get` 采样 Y 序列峰值 − 起跳前 Y ≈ 150±10；落地后归零。
6. 回退：常量改回旧值 + `FormulaVersion` 改回 3 + 还原两条轨迹文件与指纹（全部在 git 里，
   `git checkout -- <这 6 个文件>` 即回退）；Silo 重建回旧装配。

## 5. 需要用户拍板
- **是否执行方案 A**（含"客户端与服务端同批升级 + 重启本地 Silo + 重建金轨迹/指纹"）。
- 若希望先小步验证，可先只把 `HardSpeedCap`/`PositionEpsilon` 等**只影响服务端判定**的阈值改成厘米
  （不 bump 版本、不影响客户端预测），单独作为一次提交；垂直物理仍留待同批升级。
